# design-sync notes — actamundi

## Repo-specific quirks

- `components/TruthVerification.tsx` (root) and `components/truth-verification/TruthVerification.tsx` both export a `TruthVerification` component. Only the root one is actually imported anywhere in the app (`app/verify/page.tsx`); the `truth-verification/` subdir copy is unused dead code, not deleted by this sync (not this skill's call to make). `componentSrcMap.TruthVerification` is pinned to the root file to avoid ambiguity in the synth-entry scan.
- No package build exists for `components/` — it's app-internal Next.js source, not a published package. Running in **synth-entry mode**: the converter synthesizes an entry directly from `components/*.tsx`. `.d.ts` prop contracts will be weaker than a real build would give (per the skill's own caveat).
- Fonts are loaded via `next/font/google` in `app/layout.tsx` (Bodoni Moda, Lato), which generates hashed static files at Next.js build time (`.next/static/media/...`) and injects `--font-bodoni-moda`/`--font-lato` CSS variables — not discoverable by a static scrape of `app/globals.css` or `tailwind.config.js`. Expect `[FONT_MISSING]` during validate; resolve via direct Google Fonts sourcing into `cfg.extraFonts`, since these are real brand fonts the repo expects, not a substitutable choice.
- **CRITICAL — `app/globals.css` is Tailwind v3 SOURCE, not compiled output.** It only contains `@tailwind` directives + hand-written custom properties/base styles — every `className="rounded-full bg-primary ..."` utility class used throughout `components/**` is *generated* by Tailwind's own JIT compiler at Next.js build time, scanning `tailwind.config.js`'s `content` globs. Pointing `cfg.cssEntry` straight at `app/globals.css` (the naive choice, since it IS the file the app imports) ships a stylesheet with **zero utility classes** — first caught by actually looking at a rendered screenshot (every card rendered as unstyled stacked text, no padding/background/gradient), not by validate's `[CSS_RUNTIME]`/`[CSS_PLACEHOLDER]` checks, which don't catch "real file, but pre-compilation." Fixed via `cfg.buildCmd` compiling real Tailwind CSS first (see below), with `cfg.cssEntry` pointed at that compiled output.
- **`cfg.buildCmd` uses a design-sync-only Tailwind config, not the repo's `tailwind.config.js` directly**: `npx tailwindcss -c ./.design-sync/tailwind.config.synth.js -i ./app/globals.css -o ./.design-sync/.generated/tailwind.css`. `.design-sync/tailwind.config.synth.js` `require()`s the real config and extends its `content` array with `.design-sync/previews/**/*.tsx` — without this, any Tailwind class used ONLY inside an authored preview (not already present somewhere in the real app) silently fails to compile, no build error (caught via an arbitrary-value class — `bg-[#13201f]` — invisible in a screenshot despite being correctly in the JSX). **Both `.design-sync/.generated/` (gitignored build artifact) and this content-scan gap mean `cfg.buildCmd` MUST be re-run before every `package-build.mjs` invocation** — including mid-session reruns — or styling silently regresses with no error.
- **PRODUCTION BUG FOUND AND FIXED (not a design-sync artifact — verified against the live `next dev` server's own compiled CSS, independent of this tooling): `tailwind.config.js`'s entire semantic `colors` block referenced bare custom-property names (`--primary`, `--background`, `--foreground`, `--border`, etc.) that `app/globals.css` never defined — it only ever defined the `--color-*`-prefixed versions.** Every one of `bg-primary`, `bg-background`, `text-foreground`, `border-border`, `bg-card`, `bg-muted`, `bg-destructive`, `bg-secondary`, `bg-accent`, `bg-success/warning/info`, plus the entire `gray-*` scale (never had ANY primitive source, not even prefixed) and `primary-500/600/700/800`/`secondary-500/600/700` (gradient-stop utilities, `from-`/`to-`) resolved to `hsl(var(--undefined))` — a browser-silent invalid declaration — **site-wide, in production, predating this session's work.** Fixed with a minimal additive alias block in `app/globals.css`'s `:root` and `.dark` (pure forwarding, `--primary: var(--color-primary);` etc. — no existing name/value changed) plus a `gray-*` → `warm-gray-*` and `secondary-500/600/700` → `warm-gray-500/600/700` mapping (reusing the existing primitive scale, not inventing a new palette). Verified fixed in the live Next.js dev server's hot-reloaded CSS, not just the design-sync compile.

## Re-sync risks

- `cfg.cssEntry` points at a gitignored generated file (`.design-sync/.generated/tailwind.css`) that does not exist on a fresh clone or after any `git clean`. **Always run `cfg.buildCmd` first** — `package-build.mjs` does not run it automatically; the "Re-syncs are one command" driver flow in the base skill handles `cfg.buildCmd` re-runs, but any MANUAL/ad-hoc `package-build.mjs` invocation (e.g. mid-session iteration) must run it manually first, or Tailwind utility classes silently vanish from every preview with no build error.
- The `.design-sync/tsconfig.synth.json` path-alias shims (`next/image`, `next/link`, `next/navigation`, `@sentry/nextjs`) are hand-matched to actamundi's CURRENT usage (grep'd once, not derived from the .d.ts). If a future component adds a NEW `next/*` or Sentry import not covered here, expect the same `[UNRESOLVED_IMPORT] fs, stream, zlib` esbuild crash this session hit (traced via a throwaway esbuild metafile debug script, not from the error message alone — the error only names the deepest unresolvable file, not the importer chain). Re-grep `from 'next` / `Sentry\.` under `components/` on any [UNRESOLVED_IMPORT] and extend the shim set in `.design-sync/shims/` + `tsconfig.synth.json` paths.
- The `source-kit.mjs` fork's `DUPLICATE_FILES` exclusion set is hardcoded to the one known `TruthVerification` collision. If the repo ever grows a second same-named-export collision elsewhere, it'll silently reproduce the "ambiguous `export *` drops the name" bug (ES module spec, not a converter bug) with no error from validate — `[BUNDLE_EXPORT]` is the only signal, and that only fires for a deliberate validate run, not the build step.
- If a future component uses a numbered-scale color utility (`bg-X-NNN`, `from-X-NNN`, etc.) beyond what's currently aliased in `app/globals.css`'s bare-name block, it'll silently resolve to nothing (same failure mode as the production bug above) — the alias list was built by grepping current usage, not derived exhaustively. Re-grep `(bg|text|border|from|to|via)-(primary|secondary|accent|gray|success|warning|info|error)-[0-9]+` under `components/`+`app/` and extend the alias block if a gap appears.
- `--color-foreground: 200 30% 10%` is a genuinely blue-leaning hue (desaturated navy) despite the "warm-gray" brand language elsewhere in the token system — confirmed real (not a rendering bug) by pixel-sampling Select-family screenshots. Don't mistake it for an unstyled-fallback blue if it looks off in a future review.
